### 1.1 Decisão auditada — o literal `src="nativebeta"` é PRESERVADO (contrato de backend)
O app grava `src: "nativebeta"` em task/event/chat como **marcador de origem**. O backend **ramifica no valor
exato**:
- `functions/index.js:82` → `if (doc.src !== "nativebeta") return;`
- `functions/index.js:195` → `if (msg.src !== "nativebeta") return;`
- `cloudflare-worker.js:451` → `if (doc.src !== "nativebeta") continue;`

Mudar esse valor **desligaria as notificações push** dos itens criados pelo app nativo (o backend os trataria
como não-nativos). Como é proibido alterar backend/notificações/contratos, os **3** marcadores
(`TaskContract.kt`, `EventContract.kt`, `ChatRepo.kt`) **permanecem `"nativebeta"`**. Isso é **dado de
origem**, não identidade de pacote. A prova "sem nativebeta no artefato" (§4) é escopada ao **PACOTE**
`br.com.idseven.agenda.nativebeta`, que fica ausente; o literal `nativebeta` (marcador `src`) é reportado
separadamente como esperado.

## 2. Assinatura OFICIAL (sem fallback, fail-closed)

`app/build.gradle` resolve a chave **exclusivamente** de variáveis de ambiente (Secrets do CI):
`ANDROID_OFFICIAL_KEYSTORE_FILE` (`.p12` decodificado no runner) + `…_PASSWORD` + `ANDROID_OFFICIAL_KEY_ALIAS`
+ `ANDROID_OFFICIAL_KEY_PASSWORD`. Nunca versionada, hardcoded ou logada.

- `signingConfigs.official` só é **registrado** quando **todos** os Secrets existem (`storeType PKCS12`,
  v1+v2+v3 signing). O release usa `signingConfigs.official`; sem Secrets → `signingConfig null`.
- **Proibido fallback** para `idseven-test.keystore` / `debug.keystore` / assinatura de teste / senha
  hardcoded. O `debugtest` (keystore de teste versionado) fica **restrito a debug/QA local** e **nunca** é
  referenciado pelo release.
- **Fail-closed em 2 camadas:** (1) **config-time** — pedir `assemble/bundleRelease` sem Secrets aborta
  antes de compilar; (2) **execution-time** (`doFirst` em `packageRelease/packageReleaseBundle`) — rede de
  segurança. Mensagem `NO-GO F4.2E …`. O CI **prova** isso (roda release sem Secret e confirma o abort).

## 6. Plano — autenticação silenciosa da Desktop (Firebase Auth)
Requisito para a distribuição geral segura (Rules de menor privilégio dependem de `request.auth` real em
**todos** os clientes):
- A Desktop deve obter `request.auth` **silenciosamente** (sem UI extra) reusando a sessão já autenticada:
  login server-side → `issueFirebaseAuthToken` (Custom Token, o **mesmo** endpoint que o Android usa) →
  `signInWithCustomToken` no SDK Firebase da Desktop → renovação/observador de token → logout limpa.
- Escopo isolado (sem tocar update-notifications/presence já existentes), com testes de sessão/UID
  divergente/expiração/reconexão, e **flag** até prova física. Implementação em **fase própria, sob
  autorização literal** (não faz parte da F4.2E; a F4.2E **não** altera a Desktop).

## 7. Matriz final das Firestore Rules (alvo de menor privilégio) — **NÃO alterada nesta fase**
Rules **não** são modificadas na F4.2E. Alvo (a publicar em fase dedicada, gated, pós-prova de `request.auth`
silencioso na Desktop):

| Coleção | Operação do app (autenticado via Custom Token, `request.auth.uid` = UID) | Regra alvo (menor privilégio) |
|---|---|---|
| `users/{uid}` | ler o próprio perfil / equipe conforme função | `read` autenticado; `write` só do próprio doc (`request.auth.uid == uid`) via backend |
| `events/{id}` | criar/ler/editar eventos do usuário/equipe | `request.auth != null` + escopo por participante/dono |
| `tasks/{id}` | criar/ler/editar tarefas; grava `src` | `request.auth != null` + escopo por participante/dono |
| `chats/{id}/messages/{m}` | enviar/ler mensagens; `by == meId`, grava `src` | `request.auth != null`; `create` com `by == request.auth.uid` |

**Regra transversal:** nenhuma leitura de senha/hash/salt no cliente (garantido pelo gate de blindagem);
escrita de FCM token só via `registerFcmToken` (sem write direto). **Não** declarar distribuição geral segura
enquanto: Desktop sem Auth silencioso; Android+Desktop sem `request.auth` real; Rules de menor privilégio não
publicadas.
