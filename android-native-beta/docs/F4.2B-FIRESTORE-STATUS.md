# F4.2B — Estado do Firestore após o login server-side (LIMITE DESTA FASE)

**Não** afirmar que o Firestore ficou seguro nesta fase.

Após o login server-side (loginUser → token → getUserSelf → sessão criptografada):

- **`request.auth` continua NULO** no Firestore para o Android — o app **não** usa Firebase Auth
  nem `signInWithCustomToken` nesta fase.
- Os **listeners atuais permanecem no modelo legado** (UsersRepo/TaskRepo/EventRepo/ChatRepo e a
  escrita de FCM token em `users/{uid}` continuam acessando o Firestore diretamente e sem
  autenticação Firebase).
- As **operações Firestore continuam sendo um bloqueio de produção**: os dados só estão protegidos
  por Rules abertas + confiança no cliente, exatamente como antes.

## NO-GO PARA PRODUÇÃO

Mesmo com todos os gates de F4.2B verdes, o APK é **NO-GO para produção** até a fase seguinte:

**F4.2C — FIREBASE CUSTOM TOKEN + AUTHENTICATED FIRESTORE + RULES MIGRATION**,
que introduz `signInWithCustomToken` (uid = doc id, sem sistema de identidade paralelo),
autentica o Firestore (`request.auth != null`) e migra as Rules por fase.

## Escopo REMOVIDO nesta fase (login)

- `db.collection("users").get()` no login — **removido** (login é server-side);
- `Crypto.verify` no login — **removido** (verificação de senha é no servidor);
- leitura de `pass`/`salt` no login — **removida**;
- sessão em texto plano — **substituída** por Android Keystore (AES-256-GCM).

## Risco registrado para F4.2C

- **Revogação server-side de sessão**: o contrato auditado da Desktop 1.0.181 **não** possui
  endpoint de logout/revogação. O logout aqui é limpeza **integral local** (token + chave do
  Keystore). A revogação real fica para F4.2C.
- **Vínculo do token FCM à identidade**: ainda não é garantia completa (Worker J6 e o contrato FCM
  não foram alterados nesta fase).
