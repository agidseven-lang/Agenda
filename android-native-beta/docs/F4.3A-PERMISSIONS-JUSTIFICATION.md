# A2 — JUSTIFICATIVA DE PERMISSÕES — Agenda ID Seven (br.com.idseven.agenda, versionCode 129 / 1.0.0)

Base verificada: `AndroidManifest.xml` (linhas 3-11) declara exatamente 7 permissões. `app/build.gradle`: minSdk 26, targetSdk 34, compileSdk 34. Cada justificativa abaixo aponta o uso REAL no código.

Resumo de sensibilidade (targetSdk 34):

| Permissão | Tipo | Exige declaração/justificativa extra na Play Console? |
|---|---|---|
| INTERNET | Normal (install-time) | Não |
| POST_NOTIFICATIONS | Runtime (Android 13+) | Não (só solicitação em runtime) |
| USE_EXACT_ALARM | Install-time restrita (política de Alarmes Exatos) | Sim — sujeita à política; app precisa ser elegível (relógio/alarme/calendário) |
| SCHEDULE_EXACT_ALARM | Especial/sensível (Android 13+ revogável) | Sim — declaração de permissão de alarme exato |
| RECEIVE_BOOT_COMPLETED | Normal (install-time) | Não |
| REQUEST_IGNORE_BATTERY_OPTIMIZATIONS | Restrita por política (isenção de gestão de energia) | Sim — sujeita a política de uso aceitável (não há formulário fixo, mas pode ser sinalizada) |
| USE_FULL_SCREEN_INTENT | Especial/sensível (Android 14 / API 34+) | Sim — declaração de intenção em tela cheia |

Como targetSdk = 34, as três permissões marcadas como "especiais/sensíveis" (SCHEDULE_EXACT_ALARM, USE_FULL_SCREEN_INTENT e, pela política de Alarmes Exatos, também USE_EXACT_ALARM) recaem plenamente nas regras do Android 13/14 — confirmado.

---

1) android.permission.INTERNET

- O que permite: abrir sockets/conexões de rede (HTTP/HTTPS).
- Por que este app precisa (uso real): toda a arquitetura é online. Login server-side via OkHttp/Retrofit para o Cloud Run (`data/auth/AuthApiClient.kt`, `AuthApi.kt`: loginUser/getUserSelf/changePassword/issueFirebaseAuthToken/registerFcmToken); leitura/escrita de dados no Firestore (`data/EventRepo.kt`, `TaskRepo.kt`, `UsersRepo.kt`, `ChatRepo.kt`, `AuthRepo.kt`); push via Firebase Cloud Messaging (`core/AppFirebaseMessagingService.kt`); download da foto/avatar do responsável (URL http) na tela de lembrete (`core/ReminderAlarmActivity.kt`). O manifesto também força `usesCleartextTraffic="false"` + `networkSecurityConfig` (linhas 20-21), ou seja, tráfego só por TLS.
- Sensível/declaração extra: Não. Permissão normal, concedida na instalação.
- Redação para o formulário: "O aplicativo é um cliente online de agenda corporativa. Usa a internet para autenticar o usuário no backend (Cloud Run), sincronizar compromissos, tarefas, equipe e mensagens no Cloud Firestore e receber notificações push (FCM). Todo o tráfego é HTTPS/TLS (cleartext desativado)."

2) android.permission.POST_NOTIFICATIONS

- O que permite: exibir notificações ao usuário (obrigatória para postar a partir do Android 13/API 33).
- Por que este app precisa (uso real): o app posta notificações locais e remotas. Solicitação em runtime feita em `core/MainScaffold.kt:133` (`notifLauncher.launch(Manifest.permission.POST_NOTIFICATIONS)`, gated por `Build.VERSION.SDK_INT >= 33`); verificação em `Notifications.hasPostPermission()` (`core/Notifications.kt:122-124`), usada antes de qualquer `notify(...)`. Conteúdo: notificação imediata de novo compromisso/tarefa/mensagem atribuída (FCM → `AppFirebaseMessagingService.onMessageReceived`) e o lembrete local de 1h antes (`ReminderReceiver` → `Notifications.notifyReminderFullScreen`).
- Sensível/declaração extra: Não exige declaração especial na Play Console — é permissão de runtime; basta a solicitação ao usuário (já implementada).
- Redação para o formulário (se solicitado): "Para notificar o usuário sobre compromissos/tarefas atribuídos, novas mensagens da equipe e o lembrete de 1 hora antes do compromisso. A permissão é solicitada em tempo de execução no Android 13+."

3) android.permission.USE_EXACT_ALARM

- O que permite (Android 13+/API 33): agendar alarmes exatos como permissão de instalação, para apps cuja função principal é relógio/alarme/calendário/lembretes — sem depender de concessão do usuário.
- Por que este app precisa (uso real): o lembrete precisa disparar no minuto exato (1h antes do compromisso, ou no vencimento da tarefa). Agendamento em `core/ReminderScheduler.schedule()` via `AlarmManager.setExactAndAllowWhileIdle(RTC_WAKEUP, ...)` (`ReminderScheduler.kt:245`). A função de agenda/lembretes é central ao produto.
- Sensível/declaração extra: Sim. Está sujeita à política de "Alarmes exatos" do Google Play. O app só pode declará-la se um relógio/alarme/calendário/agenda for funcionalidade central — o que é o caso (lembretes de compromissos e tarefas). Nota técnica: USE_EXACT_ALARM é a variante install-time do Android 13+; quando concedida, o app não precisa do fluxo de usuário do SCHEDULE_EXACT_ALARM.
- Redação para o formulário: "A funcionalidade central do app inclui uma agenda com lembretes que devem disparar em horário exato (1 hora antes de cada compromisso e no vencimento de cada tarefa). Usamos AlarmManager.setExactAndAllowWhileIdle para garantir a pontualidade do lembrete mesmo com o app fechado ou o dispositivo em Doze."

4) android.permission.SCHEDULE_EXACT_ALARM

- O que permite: agendar alarmes exatos. No Android 12 (API 31-32) é pré-concedida; no Android 13+ (API 33) NÃO é pré-concedida e é revogável pelo usuário.
- Por que este app precisa (uso real): mesmo fluxo de lembrete exato do item 3. O código trata explicitamente o estado revogável: `Notifications.canExactAlarm()` chama `AlarmManager.canScheduleExactAlarms()` (`Notifications.kt:138-142`); `ReminderScheduler.schedule()` faz fallback para `setAndAllowWhileIdle` quando não permitido (`ReminderScheduler.kt:242-251`); e `Notifications.openExactAlarmSettings()` abre `Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM` para o usuário reconceder (`Notifications.kt:154-163`).
- Sensível/declaração extra: SIM — exige declaração de "permissão de alarme exato" na Play Console, e a mesma elegibilidade da política de Alarmes Exatos (função de relógio/calendário/agenda). Confirmado pelo targetSdk 34.
- Redação para o formulário: "O aplicativo é uma agenda corporativa cujos lembretes precisam disparar em horário exato (1h antes do compromisso; no vencimento da tarefa), inclusive com o app fechado. Declaramos SCHEDULE_EXACT_ALARM para o agendamento exato via AlarmManager; quando o usuário não concede, o app degrada para alarme inexato e oferece atalho para reativar. É funcionalidade essencial ao propósito do app (agenda/lembretes)."

5) android.permission.RECEIVE_BOOT_COMPLETED

- O que permite: receber o broadcast de que o dispositivo terminou de inicializar (e correlatos), para o app executar código logo após o boot.
- Por que este app precisa (uso real): o Android zera todos os alarmes do AlarmManager no reboot e na atualização do app. `core/BootReceiver.kt` (registrado no manifesto, linhas 55-64, para BOOT_COMPLETED, LOCKED_BOOT_COMPLETED, MY_PACKAGE_REPLACED, QUICKBOOT_POWERON) chama `ReminderScheduler.rearmAll(context)`, que relê os payloads persistidos em SharedPreferences e reagenda os lembretes futuros (`ReminderScheduler.rearmAll`, `ReminderScheduler.kt:181-209`). Sem isso, todos os lembretes se perderiam após reiniciar o aparelho.
- Sensível/declaração extra: Não. Permissão normal; não há formulário específico na Play Console. Recomenda-se apenas mencioná-la na justificativa geral de lembretes.
- Redação para o formulário (se solicitado): "Re-agendar os lembretes locais (AlarmManager) após reinicialização do dispositivo ou atualização do app, já que o Android descarta os alarmes agendados nesses eventos. Nenhum outro processamento ocorre no boot."

6) android.permission.REQUEST_IGNORE_BATTERY_OPTIMIZATIONS

- O que permite: exibir o diálogo do sistema pedindo para isentar o app da otimização de bateria (Doze/App Standby), de forma que alarmes/lembretes não sejam adiados/cancelados enquanto o app está "dormindo".
- Por que este app precisa (uso real): entrega confiável do lembrete com o app fechado, sobretudo em OEMs agressivos (ex.: Samsung/Xiaomi). `Notifications.openBatteryOptimizationSettings()` dispara `Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` (`Notifications.kt:173-188`); `Notifications.isIgnoringBatteryOptimizations()` consulta o `PowerManager` (`Notifications.kt:166-169`) e o estado é mostrado ao usuário em `features/profile/ProfileScreen.kt:165`. O pedido é opcional e sob controle do usuário (não é forçado).
- Sensível/declaração extra: Sim, em termos de política. O Google Play restringe o uso do prompt direto de isenção de bateria a casos de uso aceitáveis (alarmes/lembretes/agendas figuram entre eles). Não há um formulário fixo dedicado como o de alarme exato, mas a permissão pode ser sinalizada na revisão; a justificativa deve deixar claro o enquadramento (lembretes pontuais). Se a revisão pedir remoção, o app continua funcional (degrada para alarme inexato).
- Redação para o formulário: "O app é uma agenda com lembretes que precisam disparar pontualmente mesmo com o app fechado. Oferecemos ao usuário (opcionalmente, via diálogo do sistema) a isenção da otimização de bateria para evitar que o Doze/App Standby adie ou cancele os alarmes de lembrete. O pedido é iniciado pelo usuário e o app permanece utilizável se ele recusar."

7) android.permission.USE_FULL_SCREEN_INTENT

- O que permite: exibir uma notificação em tela cheia de alta prioridade (estilo "chamada/alarme"), que acende a tela e aparece sobre a tela de bloqueio.
- Por que este app precisa (uso real): o lembrete de 1h antes é apresentado como uma "chamada" em tela cheia — `core/ReminderAlarmActivity` (manifesto linhas 41-49: `showWhenLocked`, `turnScreenOn`, `singleTask`, `excludeFromRecents`) exibe a `ReminderPremiumScreen`; a notificação usa `setFullScreenIntent(pi, true)` no canal de alarme (`Notifications.notifyReminderFullScreen`, `Notifications.kt:288`). O código já respeita a restrição do Android 14: `Notifications.canUseFullScreen()` chama `nm.canUseFullScreenIntent()` para API ≥ 34 (`Notifications.kt:88-92`), faz fallback automático para heads-up quando não permitido, e oferece `openFullScreenIntentSettings()` via `Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT` (`Notifications.kt:111-120`).
- Sensível/declaração extra: SIM. A partir do Android 14 (API 34) o full-screen intent só é concedido por padrão a apps de chamadas/alarme; demais apps precisam solicitar via `ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT` e a Play Console exige a declaração de uso de "notificação em tela cheia". Confirmado pelo targetSdk 34.
- Redação para o formulário: "O app usa notificação em tela cheia exclusivamente para o lembrete de compromisso/tarefa de alta prioridade (1 hora antes / no vencimento), apresentado como um alerta tipo alarme que acende a tela e aparece sobre o lockscreen — comportamento essencial para o usuário não perder o compromisso. No Android 14+ respeitamos canUseFullScreenIntent(): quando não permitido, degradamos automaticamente para notificação heads-up e oferecemos ao usuário o atalho para conceder a permissão."
