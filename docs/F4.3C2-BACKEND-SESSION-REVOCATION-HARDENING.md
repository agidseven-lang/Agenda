**Escopo:** backend (`functions/index.js`), isolado, **SEM deploy**.

## 1. Problema (auditoria FASE 1)

O login server-side (`loginUser`) emite um **token de sessão HMAC** (`notifSignToken`):
`base64url(JSON(claims)) + "." + base64url(HMAC-SHA256(payload, AUTH_SESSION_SECRET))`.
A verificação (`authVerifySessionToken`) é *timing-safe*, exige `scope==="session"` e
`exp` obrigatório — **mas NÃO recarregava o usuário**. Consequência (gap):

- Um token válido **continuava aceito até expirar** mesmo após logout, troca de senha,
  desativação, exclusão ou mudança de papel/admin — não havia **revogação server-side**.
- Um token furtado (HMAC íntegro) permanecia utilizável durante toda a janela de `exp`.

Não se pode simplesmente “apagar o token” porque **o backend nunca armazena o token**
(nem hash reversível, nem Bearer). Era preciso um mecanismo de invalidação **sem
guardar segredo de sessão**.

---

## 2. Arquitetura da solução — `sessionVersion` (revogação sem armazenar o token)

Modelo escolhido (inteiro monotônico por usuário):

1. `users/{uid}` passa a carregar um inteiro **`sessionVersion`** (default `0` quando ausente).
2. O token de sessão carrega, nas **claims assinadas**, `sessionVersion` + `schemaVersion`.
3. Uma sessão só é **ATIVA** quando `token.sessionVersion === user.sessionVersion`
   **e** o usuário está ativo.
4. **Qualquer evento crítico incrementa `sessionVersion` (transação atômica)**,
   invalidando **imediatamente todas** as sessões anteriores — sem *denylist*, sem
   guardar Bearer/hash.

Eventos que incrementam `sessionVersion`:

| Evento | Handler | Campos aplicados na MESMA transação |
|---|---|---|
| Logout/revogação explícita | `revokeMySession` (novo) | `{sessionVersion+1, revokedAt}` (+ remoção FCM do device) |
| Troca de senha (logado) | `changePassword` | `{pass, salt}` |
| Reset de senha (onCall) | `confirmPasswordReset` | `{pass, salt, mustChangePassword:false, passwordChangedAt}` |
| Reset de senha (HTTP) | `confirmPasswordResetHttp` | idem |
| Admin edita usuário | `adminUpdateUser` | `patch` (allowlist) |
| Admin muda status | `adminSetUserStatus` | `{status}` |
| Admin muda admin | `adminSetUserAdmin` | `{admin}` |
| Desativação | `disableUser` | `{status:"inativo", disabled, disabledAt, disabledBy}` |
| Exclusão da própria conta | `deleteMyAccount` | `{status:"excluido", deletedAt, email:"", phone:"", photo:""}` |

Primitiva central: **`authBumpUserSessionTx(db, uid, changeFields)`** — lê o doc dentro
da transação, calcula `sessionVersion = atual + 1` e aplica `changeFields` **na mesma
transação** (sem *lost-update* sob concorrência). Em produção (`admin.firestore()` /
`notifDb()`) o caminho é **sempre transacional**; há um fallback `get+update` que só é
alcançável por *harnesses* de teste legados cujo *fake* não implementa `runTransaction`.

### Gate de REVOGAÇÃO **na ENTRADA** dos endpoints sensíveis (fecha bypasses)

O incremento **não basta**: o endpoint precisa **rejeitar a sessão stale na entrada**.
Por isso, além do *bump*, estes handlers passaram a **validar a versão/atividade ANTES**
de agir (uma sessão revogada/stale/inativa é barrada com erro uniforme, sem executar a ação):

- **`deleteMyAccount`** → exige **`authRequireActiveSession`** antes da exclusão (ação
  destrutiva). Sessão revogada/stale ⇒ `401`; usuário inativo ⇒ `403`.
- **`changePassword`** → após recarregar o doc, rejeita status inativo (`403`) e versão
  divergente (`401`) **antes** de validar a senha atual.
- **`authRequireAdminSession`** (gate de TODOS os endpoints admin) → além de recarregar e
  checar `status`/`disabled`/`admin`, valida a **versão da sessão**: uma sessão admin
  revogada (ex.: *logout-everywhere*/troca de senha, sem mudar admin/status) **perde o
  privilégio** (`401`) — a revogação vale também para o maior valor de sessão.
- **`issueFirebaseAuthToken`** e **`registerFcmToken`/`removeMyFcmToken`** → já validam a
  versão (Custom Token / registro FCM negados a sessão revogada).

### Gate de sessão ATIVA

`authRequireActiveSession(ctx)` = **verifica o token → RECARREGA `users/{uid}` →
exige status ativo (não em `["pendente","removido","excluido"]` e `disabled!==true`) →
valida a versão** (`authSessionVersionDecision`). Retorna `{ok,uid,data,role,admin,
status,sessionVersion}` ou `{ok:false,status,json,reason}` com **erro uniforme
`invalid_session`** (não revela se foi token inválido, versão divergente ou usuário
inexistente). É o gate usado pelo novo `revokeMySession` e a base recomendada para os
demais endpoints sensíveis no cutover.

## 3. `schemaVersion` + janela de migração (fail-closed)

`AUTH_SESSION_SCHEMA_VERSION = 1` marca o formato da sessão. Sessões emitidas **antes**
da F4.3C2 não têm `schemaVersion`/`sessionVersion` (LEGADAS). Decisão pura
`authSessionVersionDecision(tokenAuth, userDoc, {mode, deadlineMs, nowMs})`:

- **Token F4.3C2** (tem `schemaVersion`+`sessionVersion`): aceita **sse e somente se**
  `token.sessionVersion === user.sessionVersion`; senão `version_mismatch`.
- **Token LEGADO** (sem versão):
  - `mode="strict"` → **rejeita** (`legacy_rejected`).
  - `mode="compat"` (default) → aceita **apenas** dentro da janela
    (`nowMs <= deadlineMs`, ou deadline `0` = janela aberta) **E** se `user.sessionVersion===0`.
    Se o usuário já foi revogado/alterado (`sessionVersion>=1`), o legado é **rejeitado**
    (`version_mismatch`) — **fail-closed**: uma revogação nunca é “furada” por um token legado.

Config por ambiente (nunca pelo cliente): `AUTH_SESSION_MIGRATION_MODE` (`compat`|`strict`),
`AUTH_SESSION_MIGRATION_DEADLINE_MS`. Recomendação de cutover: manter `compat` com um
deadline curto e migrar para `strict` após a rotação natural das sessões.

---

## 4. TTL — sempre server-side

`authSessionTtlMs()` calcula o TTL **exclusivamente no servidor**. Default = **24h**
(preserva o comportamento atual; nada muda por ora). Configurável por
`AUTH_SESSION_TTL_MS` (ms), **teto absoluto 24h**, **piso 5min**. **O cliente NUNCA
influencia o TTL/`exp`.** Recomendação futura (não ativada aqui): 8h. `exp` continua
**obrigatório** na verificação (o gap de `exp` ausente já fora fechado em fase anterior).

---

## 5. `revokeMySession` (novo endpoint) — logout server-side

- Exige **sessão ATIVA** (`authRequireActiveSession`); o **`uid` vem SÓ da sessão** —
  nunca aceita `uid`/`admin`/`role`/tenant do corpo.
- Incrementa `sessionVersion` (transação atômica) → invalida **todas** as sessões
  anteriores do usuário. Opcionalmente remove os tokens FCM do `deviceId` informado
  **na mesma transação**.
- **Idempotente por estado:** após revogar, o próprio token fica obsoleto; uma 2ª
  chamada com o mesmo token retorna `401` (sessão já inválida) — sem duplo incremento.
- Resposta sem dados sensíveis (`{ok:true, revoked:true}`); `Cache-Control: no-store`.
- Wrapper `onRequest` (não usa `request.auth`); DORMENTE sem `AUTH_SESSION_SECRET` (`401`).

---

## 6. FCM — registro/remoção com gate de sessão ativa

`registerFcmToken` e `removeMyFcmToken` passam a validar, **dentro da própria
transação**, que o usuário está ativo **e** que a sessão não foi revogada
(`authSessionVersionDecision`). Sessão revogada/stale → `401 invalid_session`;
usuário inativo → `403 user_inactive`. Assim um token furtado/obsoleto não consegue
mais registrar/remover devices.

---

## 7. Rate limiting — interface substituível

- O rate-limit do **login/notif** (`notifRl*`) é **preservado byte-a-byte**
  (in-memory, por instância, sem PII).
- Novo **`createRateLimiter(opts)`** expõe a interface `{blocked, fail, clear, snapshot}`
  (in-memory por instância). `snapshot()` só devolve `{fails, until}` por chave — **prova
  estrutural de ausência de segredo** (nunca token/senha/Bearer no estado).
- Operações **ADMIN** ganham um limiter dedicado (`__adminRateLimiter`, 30/60s por `uid`
  de admin), injetável por `ctx.rateLimiter` para teste.
- **Limitação conhecida (documentada):** o estado é **por instância** (Gen2 reusa
  instâncias). Para proteção **distribuída**, um adaptador **persistente** (Firestore/
  Redis) implementaria a **mesma interface** — projetado para plug-in, **não provisionado
  nesta fase** (sem Redis, sem banco novo, sem dependência externa).

## 8. Observabilidade — auditoria sanitizada

`authAuditEvent(type, fields)` emite **somente** uma *allowlist* de campos seguros:
`event`, `correlationId`, `uid` **MASCARADO** (`notifMaskUid`), `status`, `endpoint`,
`sessionVersion`, `at`. **Qualquer outro campo é descartado.** Tipos permitidos:
`login_success`, `login_failure`, `session_revoked`, `session_version_mismatch`,
`user_disabled`, `password_changed`, `firebase_token_issued`, `fcm_registered`,
`fcm_removed`, `admin_role_changed`. Cada request carrega um `correlationId`
(`authNewCorrelationId`, `crypto.randomUUID`).

**NUNCA logado/emitido:** `AUTH_SESSION_SECRET`, token de sessão bruto, senha, salt,
Bearer completo, Firebase Custom Token, Firebase ID Token, token FCM, código de reset,
corpo completo, e-mail/telefone (nos resets, o e-mail vira `emailHash =
sha256Hex(email).slice(0,12)`). Teste dedicado prova que token/senha/body/Bearer não
aparecem no evento.

---

## 9. O que NÃO é armazenado / NÃO é alterado

- **Não armazena:** token de sessão bruto, hash reversível de sessão, Bearer completo,
  Firebase Custom Token, Firebase ID Token. Só o **inteiro `sessionVersion`** no doc.
- **Segredo inalterado:** `AUTH_SESSION_SECRET` não é rotacionado nesta fase.
- **Sem TTL do cliente.** Sem Redis/banco novo/deploy/dependência externa.

---

## 10. Compatibilidade de contrato & harnesses

- `authVerifySessionToken` só adiciona `schemaVersion`/`sessionVersion` ao retorno
  **quando presentes no token**; tokens LEGADOS mantêm o **shape exato**
  `{ok,uid,admin,role,scope}` (contrato preservado).
- Alguns `typeof X === "function"` / `typeof X !== "undefined"` guardam referências aos
  novos símbolos. **Em produção o módulo carrega inteiro** (CommonJS: ou carrega tudo, ou
  falha e nenhum endpoint sobe) → **todos os gates ficam sempre ativos**. Os guards só
  afetam *harnesses* unitários pré-F4.3C2 que avaliam **subconjuntos** de funções sem
  linkar os símbolos novos. **Não há bypass em produção.** A observabilidade (audit/cid)
  é envolvida em `try/catch` pelo princípio “telemetria nunca quebra o caminho da request”.
