# FASE 2 — Mapa Firestore da Desktop 1.0.191 (`9aaff13`)

## 2.1 VEREDITO DE AUTH (load-bearing, PROVADO)
**A Desktop 1.0.191 NÃO estabelece `request.auth`. Toda operação Firestore (renderer e main) roda com `request.auth == null`. Não há Firebase Authentication em lugar algum.**
- Renderer carrega só `firebase-app-compat.js` + `firebase-firestore-compat.js` (`desktop/src/renderer/index.html:2310`); **não** carrega `firebase-auth-compat.js`. Comentário explícito: *"Login custom s2:/SHA-256 (sem Firebase Auth)"* (`:2314`).
- Main importa só `firebase/app` + `firebase/firestore` (`desktop/src/main/firebase.ts`); zero `firebase/auth`.
- Grep global: **zero** `getAuth(`/`signInWithCustomToken`/`onAuthStateChanged`/`.auth(`. O experimento F4.2F/1.0.185 foi **removido** (o teste `desktop/scripts/f351f-rollforward-equivalence.test.mjs` **exige** a ausência desses deltas).
- O "auth" existente é **próprio, server-side** (Cloud Run `loginuser/getuserself/changepassword`); o Bearer fica confinado ao processo main (`session.json`, 0600), **nunca** no renderer nem no Firestore.

**Consequência dura:** as Rules que a Desktop 1.0.191 exercita **precisam continuar permitindo acesso anônimo** a `usersPublic` (read), `events` (read+write) e `tasks` (read+write). **Qualquer regra que passe a exigir `request.auth != null` nessas coleções quebra o Golden Master imediatamente.** (Isto é exatamente o que a suíte 07 da F4.3C3 provou: Rules-alvo deny-by-default → DENY em 100% da Desktop.)

## 2.2 Operações (resumo; tabela completa na auditoria de origem)
- **Renderer** (`index.html`, SDK compat) — **23 `collection()`** = `usersPublic`×1 (listener `:2588`) + `events`×6 + `tasks`×16 (confirmado independentemente):
  - `usersPublic`: **listener** (roster). Nunca escreve.
  - `events`: listener + `add`(novo) + `update`(editar/lifecycle/pré-delete) + `delete`.
  - `tasks`: listener + `add`(saveTask) + `db.batch()`(saveCardsBatch, atômico) + muitos `update` (moveStatus, sendToDesigner, saveProduction, clientReviewAction, persistClientSend, editar prazo…) + `delete` + **`set{merge}` de `clientReviewToken/clientReviewUrl`** (Card Premium).
- **Main** (`*.ts`, SDK modular) — **somente leitura** via `onSnapshot`: `notifier.ts` (tasks×3, events×1), `slaScheduler.ts` (tasks), `reminder.ts` (events). **Nenhuma escrita no main.**
- **Sem** `where/orderBy/limit/transaction` em nenhuma operação (só listeners de coleção inteira ou `doc(id)`).

## 2.3 O que a Desktop EXIGE das Rules (invariantes de compatibilidade)
1. **Leitura anônima** de `usersPublic`, `events`, `tasks`.
2. **Escrita anônima** de `events` e `tasks` (create/update/delete/batch, incluindo `set{merge}` do token).
3. **NÃO** lê `users` cru → `users` pode fechar sem afetar a Desktop (afeta roster Android/web).
4. **NÃO** toca `chats/messages` → chats pode endurecer sem afetar a Desktop (afeta web/Android).
5. **Nenhum índice composto** → endurecimento não cria dependência de índice.
6. A Desktop **respeita a forma** dos docs: no create escreve `by/createdAt/src`; nos updates **não** altera `by/createdAt/src` (escreve `status/history/designerSla/...`). → **endurecimento de FORMA das escritas anônimas é compatível** com a 1.0.191 (não exige auth).

## 2.4 Categorização (tags)
`usersPublic/events/tasks` = **[SHARED-WITH-ANDROID]**. Escritas de `tasks` de conteúdo/produção/token = **[CARD-PREMIUM]/[WORKER]/[PORTAL]**. Listeners do main = **[NOTIF]/[SLA] [DESKTOP-ONLY produtor]**. Notificações/SLA **não têm coleção própria** — são derivadas dos snapshots de `tasks/events` (estado em localStorage; push FCM é do Worker/triggers, não da Desktop).

# FASE 3 — Alternativas de migração (avaliação, sem implementar)

**Tensão central (provada):** a Desktop 1.0.191 exige acesso **anônimo** a `events/tasks/usersPublic`; as Rules-alvo (deny-by-default) exigem `request.auth`. São mutuamente exclusivas **para a mesma coleção ao mesmo tempo**. Logo, **não é possível exigir auth em `events/tasks/usersPublic` enquanto a 1.0.191 estiver em produção**, e a 1.0.191 **não pode** ser alterada. A Desktop só "migra" **lançando uma versão nova** (A) ou tendo seu acesso **intermediado** (B, que também exige versão nova). Coleções que a Desktop **não** toca podem endurecer já (D).

## Alternativa A — Futura Desktop autenticada (versão nova, ex.: 1.0.192+)
- **Mecanismo:** nova versão adquire **Firebase Custom Token** após login explícito (`loginUser → issueFirebaseAuthToken → signInWithCustomToken`), anexando `request.auth` a todas as ops. Idêntico ao Android f43c1.
- **A favor:** a ponte `issueFirebaseAuthToken` **já existe e está provada** (nenhuma mudança de backend). A Desktop já lê `usersPublic` (não `users`) e já grava `by` no create → **majoritariamente compatível** com as Rules-alvo. Preserva **listeners em tempo real** (onSnapshot com auth funciona).
- **Riscos:** repetir o **incidente 1.0.185** (F4.2F — bridge de Firebase Auth silenciosa que afetou o Card Premium e foi revertida na 1.0.186). Mitigação obrigatória: auth **explícita** (pós-login, não silenciosa) + **QA físico** de Card Premium, notificações, Cronograma, Roteiro, Edição de Cards e updater. A nova versão teria de tocar `firebase.ts` (init do Firestore no main — arquivo do contrato de notificações) → exige revalidação física do `notifier/slaScheduler`.
- **Desktop 1.0.191:** intacta e disponível para rollback (coexistência).
- **Veredito:** **DESTINO preferido.** Único caminho que permite fechar `events/tasks/usersPublic` sem quebrar cliente. Exige versão nova + canário + QA físico + autorização própria.

## Alternativa B — Gateway server-side (Admin SDK)
- **Mecanismo:** ops Firestore da Desktop passam a chamar endpoints backend (Admin SDK bypassa Rules); Rules fecham ao cliente.
- **Problema crítico:** a Desktop depende **fortemente de listeners em tempo real** (renderer + 6 listeners no main para notifier/SLA/reminder). Admin SDK sobre HTTPS **não dá push em tempo real** → exigiria polling/streaming (re-arquitetura enorme) e **degrada notificações/SLA** (latência, mudanças perdidas). Também exige **versão nova** da Desktop (mais invasiva que A), aumenta latência/custo (cada op = invocação de função), perde cache offline, e **re-arquiteta a escrita do `clientReviewToken`** (o exato caminho que quebrou na saga 1.0.185/186).
- **Veredito:** **INVIÁVEL — NOTIFICAÇÕES EM RISCO** (remove os listeners dos quais `notifier/slaScheduler/reminder` dependem) **e eleva o risco do Card Premium**. **Dominada por A** (mais complexa, sem ganho de segurança sobre A). Rejeitada como estratégia principal; no máximo uso pontual para uma escrita sensível específica.

## Alternativa C — Camada de compatibilidade paralela (temporária)
- **Mecanismo permitido:** **endurecimento de FORMA das escritas anônimas** em `events/tasks` (imutabilidade de `by/createdAt/src`, allowlist de campos/status, caps de tamanho, catch-all deny) **mantendo a leitura/escrita anônima** — com **sunset explícito** (prazo documentado) rumo a A.
- **Proibido (e respeitado):** acesso anônimo amplo novo, bypass permanente, token universal, exceção por User-Agent, segredo embutido na Desktop, regra aberta por tempo indeterminado.
- **Compatibilidade:** a Desktop 1.0.191 **respeita a forma** (§2.3.6) → o endurecimento de forma **passa** para a Desktop. **Ganho:** reduz mass-assignment/adulteração nas escritas anônimas. **Limite honesto:** **não** adiciona `request.auth` → **não** impede um atacante anônimo de escrever docs bem-formados. É **ponte**, não destino.
- **Veredito:** **viável como ponte temporária** (médio valor, risco baixo-médio; exige provar a conformidade de forma da Desktop e **não travar** os campos do token do Card Premium). Alimenta A.

## Alternativa D — Migração gradual por coleção
- **Mecanismo:** endurecer coleções **individualmente** conforme quem as usa. Classificação (da auditoria):

| Coleção | Pode fechar agora? | Bloqueio |
|---|---|---|
| `notifLog`, `notifPrefs`, `passwordResetCodes`, `passwordResetRequests` | **SIM** (já fechadas; manter + catch-all) | nenhum — server-only (Admin SDK) |
| `waPreviewDiagnostics` | provavelmente sim | Worker(SA) — **NÃO COMPROVADO** |
| `users` (cru) | sim para a **Desktop** (não a usa) | exige **migração roster Android→usersPublic** (+ web legada); LIVE parece já ter fechado |
| `chats` + `messages` | sim para a **Desktop** (não as usa) | exige **auth do Android/web** (participants) |
| `usersPublic` (exigir auth) | **NÃO** | exige **Desktop autenticada (A)** |
| `events` (exigir auth) | **NÃO** (forma-hardening sim, via C) | exige **A** |
| `tasks` (exigir auth) | **NÃO** (forma-hardening sim, via C) | exige **A**; **afeta Card Premium + notificações** |

- **Veredito:** **ação imediata de menor risco.** Não resolve `events/tasks/usersPublic` (isso é A), mas **tranca já** todo o resto com **zero impacto na Desktop**, e é o **framework de sequenciamento**.

## Síntese
As alternativas **não são mutuamente exclusivas**. O caminho ótimo é **D (on-ramp seguro) → C (ponte opcional com sunset) → A (destino)**, com **B rejeitada**. Ver `F4.3C4-MIGRATION-OPTIONS-MATRIX.md` para a matriz de critérios.

## 4. Card Premium — Golden Contract
**Nenhuma estratégia pode alterar ou depender de alterar:** `cloudflare-worker.js`, Worker J6, `/share`, Open Graph, `ensureReviewToken`, `ensureStableClientReviewToken`, `buildShareClientUrl`, `buildClientMessage`, `canSendToClient`, `openSendClientModal`, clipboard, WhatsApp, tokens, links, aprovação, portal. **Diff vazio comprovado** (§ isolamento).
- O token vive em `tasks.clientReviewToken` (a Desktop faz `set{merge}`; o Worker lê por token via **service account**, que bypassa Rules → o `/share` funciona independente de mudanças de Rules do cliente).
- **A:** o write do token passa a autenticado; o Worker (SA) segue igual. **Risco MÉDIO** (precedente 1.0.185) → **QA físico obrigatório** do Card Premium. Não é "em risco" se o QA passar.
- **C:** deve **manter graváveis** `clientReviewToken/clientReviewUrl` (não incluí-los no conjunto imutável). Risco baixo-médio.
- **D:** `tasks` segue aberta à Desktop → Card Premium **intocado**.
- **B:** re-arquiteta a escrita do token → **eleva o risco do Card Premium**.

## 5. Notificações — Golden Contract
**Nenhuma estratégia pode quebrar:** `cardsRules.js`, `slaRules.js`, `notifier.ts`, `main.ts`, `bgNotify.ts`, `tray.ts`, `firebase.ts`, `updaterService.ts`, `slaScheduler.ts`, T-30/T-10, amarelas/vermelhas, destinatários, deduplicação, clique, conclusão, reabertura.
- **Ops Firestore que as sustentam:** listeners **read-only** `onSnapshot(tasks)`×3 + `onSnapshot(events)` (notifier/reminder) + `onSnapshot(tasks)` (slaScheduler); + triggers `onTaskCreated/onEventCreated` (backend, Admin SDK). Notificações/SLA **não têm coleção própria**.
- **D / C:** mexem só em coleções não lidas pela Desktop, ou na **forma** das escritas → os **reads** (listeners) permanecem → **notificações intactas**.
- **A:** os listeners passam a autenticados (a versão nova ajusta `firebase.ts`) → **exige revalidação física** de `notifier/slaScheduler`; a 1.0.191 fica congelada.
- **B:** **remove os listeners em tempo real** → **INVIÁVEL — NOTIFICAÇÕES EM RISCO.**

## 6. Coexistência obrigatória
Qualquer estratégia deve permitir período de coexistência: **1.0.191 funcionando** (anônima); **canário autenticado** isolado; **Android** isolado; **Rules atuais** permanecem enquanto a migração não termina; **Rules-alvo** só no emulador até a promoção; **rollback sem apagar dados**; **sem migração irreversível de documentos**; **nenhum cliente bloqueado**.
- **Como comprovar:** teste de **dois clientes** contra as mesmas Rules — 1.0.191 (anônima) e canário (autenticado) — ambos operando. **Nota honesta:** durante a coexistência em `events/tasks/usersPublic` a leitura/escrita anônima **permanece aberta** (o buraco só fecha no **cutover final**, após todos os clientes migrarem); o **ganho de segurança imediato** vem de **D** (coleções que a Desktop não usa). `usersPublic` (projeção sem PII) já é a superfície seseg. correta para o roster durante toda a coexistência.

## 7. Estratégia de canário (projetar; não gerar nesta fase)
Branch separado; versão nova; **usuário canário isolado**; ambiente controlado; **dados sintéticos / coleção de teste**; rollback para 1.0.191; **Card Premium, notificações, Cronograma, Roteiro, Edição de Cards e updater testados fisicamente**; **nenhuma promoção automática**.
