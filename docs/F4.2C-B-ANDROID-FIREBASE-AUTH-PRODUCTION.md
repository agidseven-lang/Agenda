## 1. O que foi implementado (código)

Novos pacotes em `app/src/main/java/br/com/idseven/agenda/data/`:

- **`net/HttpClient.kt`** — transporte `HttpURLConnection` (sem dep nova), gate `https://` fail-closed,
  timeouts 15s/20s, falhas de transporte viram enum, **nunca loga url/token/corpo**. Interface (testável).
- **`net/Backend.kt`** — cliente dos 4 endpoints (`loginUser`/`getUserSelf`/`issueFirebaseAuthToken`/
  `registerFcmToken`), `Authorization: Bearer <session>`, mapeamento exato de erros
  (credenciais×sessão×inativo×503-dormant), anti-enumeração no login.
- **`session/SecureSession.kt` + `SessionCipher.kt` + `SecureSessionStore.kt`** — sessão persistida
  **cifrada** com chave no **Android Keystore (AES-256-GCM)**; arquivo em `filesDir` (escrita atômica);
  `clear(deleteKey=true)` no logout. Guarda token de sessão + expiração + perfil público. NUNCA guarda
  senha/hash/salt/Custom Token/ID Token.
- **`auth/FirebaseBridge.kt`** — fronteira sobre `FirebaseAuth` (`signInWithCustomToken`, `currentUid`, `signOut`).
- **`auth/AuthManager.kt`** — orquestra o fluxo obrigatório e a recuperação; wipe forte na divergência de UID.
- **`auth/Auth.kt` / `AuthMessages.kt`** — provedor (sem DI) + mensagens objetivas.
- **`fcm/Fcm.kt` + `AgendaMessagingService.kt`** — registro FCM **só pelo endpoint** `registerFcmToken`
  (Bearer da sessão), idempotente por `deviceId`; recepção de push + canal.
- **`data/Session.kt`** — reescrito como **fachada** sobre a sessão cifrada (mantém `uid/name/isLoggedIn/clear`
  + `role/isAdmin` reais).

Removidos (client-side inseguros): **`data/AuthRepo.kt`** (login por download de `users` + `register` gravando
hash/salt) e **`data/Crypto.kt`** (SHA-256/salt no aparelho). Telas atualizadas: `LoginActivity` (login
server-side; **cadastro client-side removido**), `MainActivity` (recuperação segura), `PerfilFragment`
(logout completo), `HomeActivity`/`EventFormActivity`/`EventDetailActivity` (papel real via `Perm.isAdmin`).
`UsersRepo` + `EventFormActivity` passaram a ler **`usersPublic`** (PII-free) em vez de `users`.
Hardening: `network_security_config.xml` (cleartext off) + `usesCleartextTraffic=false` + serviço FCM
`exported=false`. `build.gradle`: +`firebase-auth`, +`firebase-messaging`, `buildConfig`, `BACKEND_BASE_URL`,
versionCode 17→18.

### Fluxo de login (implementado)
`loginUser` → sessão server-side (cifrada) → `issueFirebaseAuthToken` → `signInWithCustomToken` →
valida `FirebaseAuth.currentUser` → **valida UID Firebase == UID da sessão** → `getUserSelf` → perfil/função
reais → inicializa. Divergência de UID ⇒ `signOut` + limpa sessão + limpa Keystore + bloqueia + mensagem.
Custom Token **só em memória** (nunca salvo/logado). Sem fallback ao Firestore sem Firebase Auth.

## 2. Contratos backend (confirmados no `functions/index.js`)

Projeto `agenda-id-seven`, região `us-central1`, Functions **Gen2**, base
`https://us-central1-agenda-id-seven.cloudfunctions.net/<fn>` (todos `onRequest` JSON; **não** callables).

| Endpoint | Método/Auth | Entrada | Saída | Erros-chave |
|---|---|---|---|---|
| `loginUser` | POST, sem auth | `{identifier,password}` | `{ok,session:{token,expiresAt},user{id,name,role,admin,status,photo,color}}` | 401 invalid_credentials · 403 user_inactive · 429 · **503 endpoint_disabled** |
| `getUserSelf` | GET, Bearer sessão | — | `{ok,uid,self{...role,status,reminderMinutes,hasFcmToken}}` | 401 invalid_session · 404 · 429 |
| `issueFirebaseAuthToken` | POST, Bearer sessão | — (uid vem da sessão) | `{ok,uid,firebaseToken,expiresInSec:3600}` | 401 · 403 user_inactive · 404 · 500 token_issue_failed |
| `registerFcmToken` | POST, Bearer sessão | `{token,deviceId,platform}` | `{ok,saved,count}` | 401 · 404 · 429 |

**GATE DE PRODUÇÃO (owner):** todos os handlers são **dormant/gated** no secret `AUTH_SESSION_SECRET`.
Sem o secret setado no ambiente deployado: `loginUser`→503, os demais→401. Além disso,
`issueFirebaseAuthToken` exige que a service account do runtime Gen2 tenha
`roles/iam.serviceAccountTokenCreator` (senão `500 token_issue_failed`). **Confirmar antes da prova física**
que os 4 endpoints estão deployados, o secret setado e o IAM concedido.

## 3. Mapa das operações Firestore reais (Android)

O app toca **3 coleções** (chats/notificações/movimentações são Desktop/PWA, não existem no Android):

| Tela/Classe | Coleção | Operação | Escopo atual | F4.2C |
|---|---|---|---|---|
| `UsersRepo.listen` (Equipe/Agenda/Hoje) | `users`→**`usersPublic`** | listen | coleção inteira | migrado p/ `usersPublic` (PII-free) |
| Login | `users` | get (todos) + verificação client | coleção inteira | **removido** (→ `loginUser` server-side) |
| `EventFormActivity.loadTeam` | `users`→**`usersPublic`** | get | coleção inteira | migrado p/ `usersPublic` |
| `EventRepo` (Agenda/Hoje/Detalhe) | `events` | listen (todos) + doc + create/update/delete | coleção inteira | mantido (dado org compartilhado) |
| `TasksRepo` (Hoje) | `tasks` | listen (todos) + update status | coleção inteira | mantido; "minhas tarefas" = filtro client por uid |

Todas as leituras hoje são **coleção-inteira sem `where`**. A projeção `usersPublic {id,name,role,admin,status,
photo,color}` (mantida pela trigger `syncUsersPublic`/backfill via Admin SDK) elimina a exposição de
`pass/salt/phone/email`. `events`/`tasks` são dados **organizacionais compartilhados** (não há PII por-usuário
neles); o escopo por `request.auth` fica preparado para a fase de Rules (abaixo).

## 4. MATRIZ DEFINITIVA DE FIRESTORE RULES (entregar; **NÃO publicar ainda**)

Rules de produção HOJE (fonte: `ops/firestore-rules-baseline` + trajetória `f3358b`/`f3361t1`): **abertas** —
`users` em fechamento → `usersPublic read:if true`; `events`/`tasks`/`chats` `read/write:if true`;
`request.auth` só usado em `isAdmin()`/`notif*`. **A Desktop 1.0.184 NÃO usa Firebase Auth** e depende dessas
regras abertas.

| Op | Coleção | Query | Campos | UID/Role/Escopo | Rule necessária (alvo pós-auth) | Impacto na Desktop 1.0.184 |
|---|---|---|---|---|---|---|
| Ler equipe | `usersPublic` | coleção | id,name,role,admin,status,photo,color | qualquer autenticado | `read: if request.auth != null` | **Bloqueia** se Desktop não estiver Firebase-auth |
| Ler/gravar `users` | `users` | doc próprio | perfil | `uid==request.auth.uid` | leitura só do próprio; escrita só server (Admin SDK) | Desktop hoje lê/grava `users` aberto → **quebra** sem cutover |
| Ler agenda | `events` | coleção | evento | autenticado | `read: if request.auth != null` (+ escopo por equipe futuro) | **Bloqueia** leitura da Agenda sem Firebase-auth |
| Criar/editar/excluir evento | `events` | doc | evento | admin (role) | `write: if isAdminAuth()` (role via token/claims ou users doc) | Desktop cria/edita eventos → **quebra** sem cutover |
| Ler quadro | `tasks` | coleção | tarefa | autenticado | `read: if request.auth != null` | **Bloqueia** o Quadro |
| Atualizar status tarefa | `tasks` | doc | status,startedAt,doneAt | autenticado (dono/atribuído) | `update: if request.auth != null` (+ campos permitidos) | Desktop move cards → **quebra** sem cutover |
| Chats/mensagens (Desktop/PWA) | `chats/**` | — | — | participante | por `participants` + auth | Desktop usa; endurecer exige Firebase-auth na Desktop |
| notifLog/notifPrefs | — | — | — | admin/server | inalterado | sem impacto |

**Regra do owner honrada:** endurecer qualquer uma dessas regras para exigir `request.auth` **bloquearia a
Desktop 1.0.184** (sem Firebase Auth). Portanto **NÃO publicar Rules** até Android **e** Desktop estarem
autenticados no Firebase em produção. Qualquer risco de bloquear a Desktop ⇒ NÃO PUBLICAR. Recomendação de
cutover: (a) Desktop ganha o mesmo bridge (`issueFirebaseAuthToken`+`signInWithCustomToken`) — ver §8; (b) só
então publicar Rules gated com rollback imediato para a versão aberta.

## 6. Assinatura oficial — situação + procedimento (owner gate)

**Situação atual:** o `android-native` é **debug-signed** com `~/.android/debug.keystore` **regenerado a cada
build de CI** (cert instável entre builds ⇒ não é Play-ready e não é auto-atualizável). **Não existe nenhuma
chave oficial** para o módulo oficial. (O beta usa `idseven-test.keystore` commitada com senha pública — QA
apenas; jamais produção.) **Não usar** debug.keystore / idseven-test.keystore / senha pública / cert temporário
como chave de produção.

**Como não existe chave oficial anterior, PARAR antes de gerar a primeira chave definitiva.** Procedimento
entregue para o owner executar **localmente** (a chave/senha **nunca** trafega no chat):

```
# 1) Gerar a chave de UPLOAD oficial (RSA 4096, validade ~27 anos), LOCALMENTE:
keytool -genkeypair -v \
  -keystore idseven-upload.jks \
  -alias idseven-upload \
  -keyalg RSA -keysize 4096 -validity 10000 \
  -storetype PKCS12
# (guardar storepass/keypass num cofre; NUNCA no repo/chat)

# 2) Fingerprints para registrar no Firebase (SHA-1 e SHA-256):
keytool -list -v -keystore idseven-upload.jks -alias idseven-upload
```

- **Alias recomendado:** `idseven-upload`. **Validade:** 10000 dias. **Tipo:** PKCS12.
- **Fingerprints SHA-1 e SHA-256:** obtidos pelo comando (2) — registrar no **Firebase Console** (app Android
  `br.com.idseven.agenda`) e informar à Play (upload key).
- **Armazenamento/secrets:** manter a `.jks` **fora do repo**; no CI, injetar via secrets
  (`ANDROID_UPLOAD_KEYSTORE_BASE64`, `ANDROID_UPLOAD_KEY_ALIAS`, `ANDROID_UPLOAD_STORE_PASSWORD`,
  `ANDROID_UPLOAD_KEY_PASSWORD`) — o build lê do env, nunca de arquivo versionado.
- **Recuperação/backup:** backup cifrado offline em 2 locais; **Play App Signing** habilitado (o Google guarda a
  chave de *assinatura*; a de *upload* é recuperável via reset se registrada). 
- **Impacto permanente da perda:** sem Play App Signing, perder a chave de assinatura = impossível atualizar o
  app (usuários teriam de desinstalar/reinstalar). **Por isso: habilitar Play App Signing** (upload key
  recuperável) e fazer backup da upload key.

**Nenhuma chave gerada nesta fase.** Aguardando decisão do owner.

## 8. Plano da autenticação silenciosa da Desktop 1.0.184

Para endurecer as Rules sem quebrar a Desktop, a Desktop precisa também obter identidade Firebase — **de forma
silenciosa** (sem novo login), reaproveitando a sessão server-side que ela já tem:

1. No bootstrap/login da Desktop (Electron), após obter a sessão (`loginUser`/sessão persistida), chamar
   `issueFirebaseAuthToken` (Bearer da sessão) → `firebaseToken`.
2. No **main process** (onde já vive o updater/notificações), inicializar o Firebase JS SDK e
   `signInWithCustomToken(firebaseToken)`; validar `currentUser.uid == uid da sessão`.
3. Renovação pelo próprio SDK (ID token auto-refresh); Custom Token só em memória; nunca persistir ID token.
4. Só depois que **Android E Desktop** estiverem autenticados em produção, publicar as Rules gated (com rollback
   imediato para a versão aberta). Enquanto isso: **Rules abertas preservadas** (Desktop 1.0.184 intacta).
5. Entregue como **plano** (nenhuma mudança na Desktop nesta fase — mandato de preservação).
