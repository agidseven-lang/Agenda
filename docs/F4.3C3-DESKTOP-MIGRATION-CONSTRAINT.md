# F4.3C3 — ARTEFATO C: Restrição de Migração (Desktop 1.0.191)

## Tese
As **Rules-alvo** (`security/firestore/f43c3/firestore.f43c3-target.rules`) são
**deny-by-default com `request.auth` obrigatório**. A **Desktop 1.0.191 (Golden Master)**
**não usa Firebase Auth** — todas as suas operações Firestore carregam `request.auth == null`.
Portanto, sob as Rules-alvo, **a Desktop recebe DENY em 100% das suas operações**.

**Isso é ESPERADO e PROVA que as Rules-alvo NÃO podem ser implantadas enquanto a Desktop
1.0.191 estiver em produção.** Não se corrige a Desktop nesta fase; não se enfraquece a
Rule; não se cria exceção anônima.

## Prova (emulador, suíte `tests/07-desktop-1.0.191.mjs`, 8/8 DENY)
Operações REAIS auditadas da Desktop (renderer `desktop/src/renderer/index.html`; main
`desktop/src/main/*.ts`), todas SEM `request.auth`:

| Op real da Desktop | Sob Rules-alvo |
|---|---|
| `onSnapshot(usersPublic)` (roster) | **DENY** |
| `onSnapshot(events)` | **DENY** |
| `events.add(...)` / `.update(...)` | **DENY** |
| `onSnapshot(tasks)` | **DENY** |
| `tasks.add(...)` / `.update(...)` (mover card) | **DENY** |
| `getDoc(usersPublic/{id})` | **DENY** |

Motivo: `usersPublic`, `events` e `tasks` exigem `isActiveUser()` (que começa por
`request.auth != null`). A Desktop não anexa token → falha na primeira condição.

## Por que NÃO adaptar a Rule à Desktop
- Rebaixar qualquer coleção para `allow …: if true` (como hoje) reabriria o buraco de PII
  (`users` com pass/salt/fcmTokens legíveis) — anula o objetivo.
- Criar exceção anônima específica p/ a Desktop = bypass permanente e não auditável.
- Modificar a Desktop 1.0.191 é **PROIBIDO** nesta fase (Golden Master congelado).

## Caminho de migração (fora desta fase — F4.3C4+)
Para as Rules-alvo poderem ser implantadas sem quebrar a Desktop, a Desktop precisaria,
em fase futura AUTORIZADA e com nova build/validação física:
1. Adotar **Firebase Auth / Custom Token** (como o Android já faz: sessão → `issueFirebaseAuthToken` → `signInWithCustomToken`), anexando `request.auth` a todas as ops Firestore.
2. Manter o roster em **`usersPublic`** (já faz) — compatível com a Rule.
3. `events`/`tasks`: manter `by == uid` na criação; não alterar `by/ownerId/createdAt/src`.

**Android (f43c1)**: já usa `request.auth` (custom token) e é **majoritariamente compatível**
com as Rules-alvo para `tasks/events/chats` — PORÉM hoje lê `users` cru (roster com
fcmTokens/PII). Sob as Rules-alvo `users` fica fechada → **Android deve migrar o roster de
`users` para `usersPublic`** (item de migração; não implementado aqui).

## Conclusão
Enquanto a Desktop 1.0.191 (e o roster cru do Android) não migrarem, **as Rules-alvo
permanecem uma PROPOSTA validada só em emulador — SEM autorização de deploy**. O ruleset
ativo em produção **não é alterado** por esta fase.
